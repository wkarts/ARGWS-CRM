# Saldo utilizável de nota de crédito cancelada

O leitor canônico retornava total menos aplicações/reembolsos como `available`, inclusive com status3. Como o cancelamento nativo só aceita documento sem histórico, isso fazia GUI, API e PDF exibirem o valor nominal inteiro como saldo disponível de um crédito cancelado. O escritor já vetava seu uso; a apresentação era incorreta. A regressão RED foi reproduzida no serviço real antes da correção.

Depois de validar o estado e a ausência de entradas, CompanyCredits retorna `available: "0.00"` para status3. `amounts.total`, itens, número, emitente/destinatário capturados, linha nativa, histórico e eventos permanecem originais. Nenhuma entrada, pagamento, crédito falso, alteração no escritor, schema ou migration é acrescentada. Estados ativos/consumidos mantêm seu cálculo exato anterior. Leitor/PDF/GUI/API usam a mesma projeção canônica corrigida.

A posição CompanyReports já excluía documentos cancelados; o diário já mantinha credit_nominal e subtraía credit_after_cancellations no evento original de cancelamento. Testes confirmam esses comportamentos existentes e que os totais atuais não crescem após emitir e cancelar100.00. O valor nominal continua no documento e no diário, sem tornar-se utilizável. Retry de cancelamento não regrava o evento e não modifica os bytes capturados.

Os testes adicionados incluem API detalhe/lista e PDF reais, A/B, crédito ativo parcial e regressão de estado recusado pelo escritor. Três corridas reais observam dois escritores aguardando no mutex: void/void, void/refund e void/apply. Há um único vencedor financeiro, ou duas confirmações do mesmo cancelamento com um evento. Browser nativo verifica status Cancelada, Total BRL100.00 e Saldo disponível0.00, ausência de formulários aplicar/reembolsar, API e PDF privados. Texto extraído do PDF real confirma100.00 nominal e0.00 utilizável.

Este pacote não muda a semântica nativa de cancelamento nem executa reembolso externo ou homologação bancária. Os testes de API exigem o pacote financeiro anterior; o hunk de produção é independente e não altera seus arquivos congelados. O bootstrap HTTP é protótipo descartável, preserva o marcador nativo e não substitui migration oficial.
