# Native whole-timer batches across projects and standalone tasks

`company_time_batches/index` is a sealed staff financial surface. It selects whole, closed native timers. A batch uses one native namespace (`projects` or `standalone`), issuer, private active client and explicit currency. Several owned projects may share one invoice only when their persisted client is the selected client. A shared directory client does not grant this authority. The company and actor come from the sealed context, never submitted issuer fields.

Standalone tasks have no native client. The first durable financial reservation explicitly binds the task to an authorized private client and currency. A first reservation without a canonical invoice receipt may be withdrawn by its owning actor, removing only its own provisional binding and claims. A confirmed binding remains after invoice edit/cancel, client transfer, native task progress and later batches. Selecting a different client/currency fails before any new invoice. Old standalone whole-task billing cannot reuse any partial allocation.

Prices can be one explicit hourly profile, explicit profiles per task, or frozen native hourly declarations per project. Every selected native project rate must match the chosen currency. Formats are one line per task, one line per independently rounded timer, or one uniform line with the same rate/rounding profile. Arithmetic reuses `CompanyTaskBillingAmounts` and `CompanyInvoiceAmounts`: integer authoritative native seconds, interval rounding, two-decimal hour quantities and exact decimal item/tax/discount/adjustment rounding. A duration is never split; zero-quantity timers in a valid positive batch remain allocated and visible in the preserved source. Native timestamp strings are retained with their existing server-local basis; they are not relabeled as UTC. Reservation/audit timestamps are UTC.

The limit is 500 selected timers, 100 emitted lines, ten taxes per line and 2MiB per request/source. The chooser has 100 timers per page and 50 private clients per page; `after=0` and `timer_after=0` are valid first-page cursors. Changing a page does not silently preserve an unreviewed selection from another page. Historical batches are available by origin ID and the last 100 batches for the selected client/namespace. Foreign IDs are rejected before financial hydration.

Prepare captures native task and project revisions, timers, native prices, tax input, client/currency and fiscal configuration, with exact raw JSON/hash plus prepared-audit metadata. It does not issue an invoice. Conversion first commits a durable intention, namespace-specific timer claims and any first standalone binding under the same issuer mutex used by earlier billing profiles. Whole-task, fixed-project, old project-time and whole standalone writers share the new fences. A contact-created434 source transitions from `unbilled` to `converting` before receipt creation; successful confirmation makes it `billed`, keeping the private contact writers closed.

`CompanyInvoices::create` remains the only invoice writer. The complete participant list and veto-only source guard run in its owned transaction. A failed canonical insert leaves an explicit resumable intention. A canonical receipt committed before a final-link failure cannot be abandoned or billed again: the same actor resumes the same receipt, even if current customer ownership or fiscal settings changed after issuance. Normal live staff/resource grants still apply. A completed retry may be read by another currently authorized actor but cannot change the captured author or invoice. Another financial intention cannot claim sibling timers while the task is pending.

After a confirmed partial invoice, native task writers may progress the task and add new timers. They do not rewrite the previously captured closed timer rows. Only unallocated closed timers can enter a later invoice. Both original declared total and current canonical invoice total/status appear in the GUI through `CompanyBillingInvoiceLifecycle`. Editing or canceling the invoice never releases confirmed claims or standalone client/currency binding. Cancellation shows zero current collectible balance while preserving original evidence. No cash, credit note or provider operation is invented.

`CompanyTaskTimeBatchSchema` adds five empty tables: `company_task_time_batch_origins`, `company_task_time_batches`, `company_task_time_batch_claims`, `company_standalone_time_claims`, `company_standalone_time_clients`. Separate native foreign-key namespaces prevent same-number project/standalone timer collisions. Ensure must run outside transactions after the native projects/tasks/standalone and earlier billing schemas. Operations validate existing InnoDB/schema/keys/collations; they never execute DDL. The official numbered migration is supplied by the integration owner. Test bootstrap ensure/replay explicitly does not advance native migration tracking.

The service/controller suites exercise A/B/principal and preserved NULL history, exact values and native PDF, mixed owner/client/currency rejection, prepared identity/digest retries, stale revisions, audit/source byte integrity, client binding withdrawal/recovery, native new timers after partial billing and invoice lifecycle. Real InnoDB contenders cover same origin, distinct overlapping origins, every earlier whole/time billing profile, conflicting standalone customer declarations and grant/customer/timer changes during lock wait. The native HTTP suite bootstraps only its self-contained disposable fixture plus existing PDO helper into a runtime with tests stripped, and uses Chromium and the real MariaDB CLI compound-trigger delimiter.

This is locally tested CRM financial provenance. It does not execute external bank payments, authenticate external bank reversals, send email, claim fiscal issuance, split a timer duration or migrate legacy/NULL tasks into a company.
